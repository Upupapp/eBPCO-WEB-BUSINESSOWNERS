# AI Frontend Development Guide

Version: 1.0.0
Status: Approved
Document Owner: Project Owner

Category: AI Development Standards

---

# Purpose

This document establishes the mandatory standards for AI-assisted frontend development within the Electronic Building Permit and Certificate of Occupancy (eBPCO) project.

It ensures that every contribution generated by AI tools (e.g., Claude AI, ChatGPT, GitHub Copilot) remains consistent with the project's architecture, design system, and coding standards.

This guide applies to both:

- Angular Web Administration Portal
- Flutter Mobile Application

---

# Objectives

The AI must:

- Produce maintainable code.
- Preserve the project architecture.
- Reuse existing components.
- Follow the Design System.
- Respect Brand Guidelines.
- Preserve navigation.
- Maintain accessibility.
- Avoid unnecessary rewrites.

---

# AI Development Workflow

Every AI task follows this sequence:

1. Understand the request.
2. Inspect the existing project.
3. Review relevant documentation.
4. Reuse existing components.
5. Implement the requested change.
6. Validate functionality.
7. Run quality checks.
8. Summarize all changes.

AI should never begin coding before understanding the existing implementation.

---

# Required Documentation

Before generating code, AI must consult:

1. Brand Guidelines
2. Design System
3. Component Library
4. UX Standards
5. Stitch Documentation
6. Feature Requirements

If documentation conflicts, follow the documented decision hierarchy.

---

# Architecture Rules

AI must preserve the existing project structure.

Do not:

- Move folders unnecessarily.
- Rename features without reason.
- Rewrite working modules.
- Introduce duplicate architectures.

Enhancements should be incremental.

---

# Component Rules

Before creating a component:

1. Search the Component Library.
2. Search shared widgets.
3. Search reusable layouts.

Reuse first.

Only create a new component when no suitable option exists.

---

# Theme Rules

All visual values must come from centralized theme files.

Never hardcode:

- Colors
- Font sizes
- Border radius
- Shadows
- Spacing
- Typography
- Status colors

---

# Navigation Rules

AI must preserve:

- Existing routes
- Existing navigation flow
- Existing deep links
- Existing screen hierarchy

Buttons must continue navigating to their intended destinations.

---

# Angular Standards

AI must:

- Use standalone components when required by the project.
- Follow the established folder structure.
- Reuse shared components.
- Reuse SCSS variables and mixins.
- Avoid duplicate services.
- Keep components focused on a single responsibility.
- Use strongly typed models and interfaces.

---

# Flutter Standards

AI must:

- Use existing providers and state management.
- Reuse shared widgets.
- Centralize theme values.
- Use responsive layouts.
- Avoid duplicated widget implementations.
- Respect SafeArea.
- Use const constructors where applicable.
- Minimize unnecessary widget rebuilds.

---

# Naming Conventions

Use descriptive names.

Examples:

Components

- UserCard
- StatusChip
- DashboardHeader

Services

- AuthService
- NotificationService

Providers

- DashboardProvider
- AuthProvider

Widgets

- PrimaryButton
- SectionHeader

Avoid abbreviations unless already standardized.

---

# Accessibility

Every generated UI must:

- Support keyboard navigation where applicable.
- Meet WCAG 2.1 AA contrast.
- Use semantic labels.
- Preserve focus states.
- Maintain readable typography.
- Use minimum touch targets of approximately 44 × 44 px.

Accessibility is mandatory.

---

# Responsiveness

AI must verify layouts for:

- Small phones
- Standard phones
- Large phones
- Tablets
- Desktop (Angular)

No overflow or clipped content should remain.

---

# Error Prevention

AI should never:

- Delete working functionality.
- Break routing.
- Remove validation.
- Introduce placeholder navigation.
- Ignore compiler warnings.
- Ignore analyzer errors.

---

# Testing Checklist

After implementation, AI should recommend or perform:

Angular

- npm install (if required)
- ng build
- ng serve
- npm test (where available)

Flutter

- flutter pub get
- flutter analyze
- flutter test
- flutter run

---

# Pull Request Checklist

Before considering a task complete:

- Existing functionality still works.
- Navigation remains intact.
- Shared components are reused.
- No duplicate widgets exist.
- No hardcoded design values remain.
- Accessibility requirements are met.
- Responsive behavior is verified.
- Code compiles successfully.
- Documentation is updated if needed.

---

# Definition of Done

A frontend task is complete only when:

- It satisfies the feature request.
- It follows the Brand Guidelines.
- It follows the Design System.
- It reuses existing components.
- Navigation remains functional.
- Responsive layouts are verified.
- Accessibility requirements are met.
- No new analyzer or compiler errors are introduced.
- Existing tests continue to pass, or any failures are documented.
- The implementation is approved by the Project Owner.

---

# AI Prompting Best Practices

When requesting AI assistance:

- Clearly describe the objective.
- Specify the target platform (Angular or Flutter).
- State whether the task is frontend only or full stack.
- Reference relevant documentation.
- Ask AI to inspect the existing implementation before making changes.
- Require preservation of existing functionality.
- Request a summary of modified files and validation steps.

---

# Governance

All AI-generated code must comply with this guide.

Any generated code that violates these standards must be revised before merging into the project.
