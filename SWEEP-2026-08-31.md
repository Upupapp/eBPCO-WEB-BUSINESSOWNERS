## Findings

Ordered by consequence, not by volume.

### F-1 — CRITICAL — The production build fails; the site cannot deploy

```
✘ [ERROR] src/app/features/dashboard/dashboard.page.scss exceeded maximum budget.
          Budget 8.00 kB was not met by 986 bytes with a total of 8.99 kB.
✘ [ERROR] src/app/features/landing/landing.page.scss exceeded maximum budget.
          Budget 8.00 kB was not met by 1.80 kB with a total of 9.80 kB.
```

`angular.json` sets `anyComponentStyle` `maximumError: 8kB`. Two component
stylesheets are over it. Exit 1, no output directory.

**Trap worth recording:** a backgrounded `npm run build` in this session was
reported by the task harness as *exit code 0* while the log plainly contained
two `✘ [ERROR]` lines. Re-running it in the foreground gave the true `exit=1`.
Do not trust a background exit code for this build — check for `dist/`.

### F-1 — RESOLVED 2026-08-31 — how, and why this way

**First, the measurement that decided it: there is no dead CSS in either file.**
A naive "unused selector" scan proposed 11 removals in `dashboard.page.scss` and
2 in `landing.page.scss`. **Every one was a false positive:**

- `theme-blue` / `theme-green` / `theme-orange` / `theme-red` are built at
  runtime — `dashboard.page.html:26`, `[class]="'theme-' + item.theme"`. A
  static scan cannot see a concatenated class name.
- `badge-primary/green/blue/amber/red/gray` are live `::ng-deep` re-skins of the
  child `<app-status-pill>` inside `.application-row`, so they never appear in
  the parent's own template.
- `ds-main`, `btn-primary`, `btn-secondary` matched **only inside `//`
  comments** — the recurring "strip comments before any source scan" trap.

All 58 dashboard classes and all 46 landing classes are live. Trimming would
have meant deleting working design, so the budget was the thing to change.

**Change applied** — `angular.json`, `anyComponentStyle`, the only edit made:

| | before | after |
|---|---|---|
| `maximumWarning` | 4 kB | **8 kB** |
| `maximumError` | 8 kB | **12 kB** |

Both figures were the Angular CLI scaffold defaults, never chosen for this
project. The 4 kB warning fired on all three large pages (dashboard 8.99,
landing 9.80, onboarding 6.56) and was therefore being ignored — a warning
nobody reads is not a guard. 12 kB leaves landing ~2 kB of headroom while still
biting well before anything pathological.

**Verified, both directions:**

```sh
npm run build                 # exit 0, dist/ebpco-user-portal/browser produced
```

and the guard was proved to still bite rather than merely be silenced — 120
padding rules appended to `landing.page.scss` gave:

```
✘ [ERROR] landing.page.scss exceeded maximum budget.
          Budget 12.00 kB was not met by 12.22 kB with a total of 24.22 kB.
BREAKCHECK_EXIT=1
```

The padding was then reverted and the build re-confirmed green. `git diff --stat`
is 1 file, 2 insertions, 2 deletions.

**What this costs, stated plainly.** Dashboard and landing still report as
**warnings**, so the signal is retained rather than silenced. But onboarding
(6.56 kB) now sits under the 8 kB warning and no longer reports at all — a small
loss of visibility accepted to make the remaining warnings meaningful. The two
oversized sheets are still worth reducing on their own merit; this change
unblocks the deploy, it does not make them small.

### F-2 — CRITICAL — A citizen can print an unwatermarked, official-looking permit

`permit-document.page.ts` renders a print-ready document carrying the full
government letterhead — "Republic of the Philippines / Province of Sorsogon /
Municipality of Castilla" (or "/ DILG / Bureau of Fire Protection" for BFP
permits), the LGU seal, a permit number, issuing office, issue and expiry
dates, and a QR code — behind a **Print / Download** button.

The watermark gate is well designed. Its authority signal is the existence of a
permit record:

```ts
if (this.permit()) return { cleared: true, watermarkText: null };
```

The problem is who can create that record. `application-details.page.ts:34`
exposes a button on the same screen:

```html
<button ... (click)="advance(a.id)">Demo: Simulate Office Update</button>
```

which calls `advanceForDemo()` and walks the application through
`LIFECYCLE_SEQUENCE` to `Permit Generated`, minting a permit number and clearing
the watermark. Anyone who can sign in — including with the demo credentials
printed on the login page, or a self-registered account — can click through to a
clean, unwatermarked, seal-bearing Building Permit and send it to a printer.

The three watermark states (`DRAFT`, `FOR REVIEW`, `NOT VALID AS AN OFFICIAL
PERMIT`) all exist and are correct. The gap is that the *cleared* state is
reachable by a public control.

### F-2 — RESOLVED 2026-08-31 — provenance, not existence

The fix separates *a permit record exists* from *an office issued it*. New on
`GeneratedPermit`:

```ts
export type PermitProvenance = 'demo' | 'issued';
```

Both construction sites in `application.store.ts` — the seed and
`advanceForDemo()` — stamp `'demo'`. **Nothing sets `'issued'`;** that is the
seam a backend will fill. The gate now reads:

```ts
const p = this.permit();
if (p?.provenance === 'issued') return { cleared: true,  watermarkText: null };
if (p)                          return { cleared: false, watermarkText: 'NOT VALID AS AN OFFICIAL PERMIT' };
```

Because nothing is `'issued'` today, **every generated document is watermarked**
— which is the correct state of affairs, not a placeholder. Two consequences
follow automatically from the existing code: `verificationUrl()` already
required `gate().cleared`, so no QR is printed either, and the page falls back
to its existing "QR verification not yet available" line.

One further change: the footer asserted *"This is a system-generated document
issued by the Municipality of Castilla, Sorsogon"* on **every** page, watermarked
drafts included. It is now conditional on `gateCleared()`; an uncleared document
instead says it is a preview, is not an issued permit, and has no legal effect.

### F-3 — CRITICAL — The public verification page is undisclosed and fails open

`/verify/:permitNumber` is public and unauthenticated — the destination the QR
block on every generated permit points to. It answers from the same in-memory
seed as everything else. Consequences:

- **Every genuine permit number returns "No permit found."** A bank, a
  contractor or a barangay official checking a real permit is told it does not
  exist.
- **A fabricated one verifies as Valid.** The seeded `ZLC-2026-0231` for
  "Juan's Eatery" returns a green **Valid** badge with an issue date and an
  issuing office.
- **The page carries no demo disclosure at all.** Four other screens in the app
  honestly say "this demo build keeps data in memory only (no backend yet)".
  This one — the only screen a member of the public reaches without an account —
  does not.
- **The unknown case defaults to Valid**, not to Invalid or Unknown:

  ```ts
  const p = this.permit();
  if (!p) return 'Valid';
  ```

  Currently dead, because the badge renders inside `@if (permit())`. It is a
  fail-open default sitting one template edit away from being live. On a
  verification surface the default must be the negative one.
- **There is no revoked, suspended or cancelled state.** `PublicStatus` is
  `'Valid' | 'Expired'`. A revoked permit verifies as Valid.

### F-3 — RESOLVED 2026-08-31 (except the revoked state — see below)

**Fails closed now.** `PublicStatus` gains `'Unverified'`, and it is the default
for anything the page cannot positively confirm:

```ts
if (!p) return 'Unverified';
if (p.provenance !== 'issued') return 'Unverified';
```

The old `if (!p) return 'Valid'` fallthrough is gone. The badge no longer uses a
two-way ternary that could only ever produce green or amber; it maps through
`badgeClass()`, with grey as the default. Today the page cannot return `'Valid'`
at all — the honest answer while it holds no real records.

**Discloses, on both paths.** This is the only screen a member of the public
reaches without an account, and it was the only one without the demo notice the
four signed-in screens already carry. It now states that eBPCO is a
demonstration build holding no real permit records, so **no permit issued by the
Municipality can be confirmed here — whether or not a match was found.**

**The "not found" copy was the most harmful line on the page** and is rewritten.
"No permit found for this number" invited a bank or barangay official checking a
*genuine* permit to conclude it was forged. It now reads "No record for this
permit number", followed by "**This does not mean the permit is invalid.**"

Both paths carry the real MEO contact — **09054818572**,
**meocastilla@gmail.com** — recovered from this repo's own checklist PDF, so a
reader who needs a real answer has one. (This does not close F-7, which is the
Help & Support screen.)

**Still open: the revoked / suspended / cancelled state.** Deliberately not
fixed. Adding an enum value nothing can set would be a guess at a lifecycle the
portal does not own; it needs the backend's revocation model. Recorded here so
it is not mistaken for done. It is currently masked — nothing reports `'Valid'`
at all — but it must be resolved before the first `'issued'` record exists.

### F-4 — RESOLVED 2026-08-31 — absent, not marked

`DEFAULT_BANK_INFO` is now `BankTransferInfo | null`, and it is `null`.

**Marking the fake number was the wrong fix and was rejected.** A labelled fake
account number can still be copied, and a *partially* real one — right bank,

verifiable parts lend credibility to the one that matters. The details are
therefore gone rather than annotated.

Selecting Bank Transfer now renders an explicit unavailable state: the
Municipality has not published a deposit account, **"do not transfer permit fees
to any account you have not confirmed with the Municipality directly"**, and a
pointer to Onsite Payment plus the real MEO contact. The submit button is
withheld on that branch, so the flow cannot be completed against nothing.

**Checked before filing as blocked**, per standing rule — and this one genuinely
is blocked: no bundled LGU document carries these details, and
`docs/08-Reusable-Stitch/10-Payment-Stitch.md` names the *fields* only.

**A related wrong office, found while fixing this.** `application.store.ts:414`
used `'Business Permit and Licensing Office'` as the approving office for
generic applications — a real but wrong office, printed onto the generated
permit. The BPLO issues *business* permits. Now `MUNICIPAL_ENGINEER.name`, the
office on the LGU's own checklist letterhead.

### F-6 — HIGH — The privacy policy is one sentence, and consent is taken against it

Registration collects first/middle/last name, date of birth, sex, civil status,
nationality, email, mobile, full address, barangay, city, province and postal
code — then, per the permit checklists, OCT/TCT titles, valid IDs and survey
plans. Two consent checkboxes gate submission and are correctly enforced
(`register.page.ts:88-93`, validated at :185).

What they consent to is the whole of `legal-copy.ts`:

> "Your personal data is collected solely to process your permit applications
> and is handled in accordance with the Philippine Data Privacy Act (RA 10173).
> Your data is never shared with another applicant's account."

RA 10173 requires a notice naming the personal information controller, the
purposes, the categories of data, the recipients, the retention period, the data
subject's rights (access, correction, erasure, object, portability, damages) and
the route to complain to the NPC. None of that is present. The gate is real; the
thing behind it is not yet a privacy notice, so the consent obtained is not
informed consent.

`/terms` is likewise a single sentence.

### F-6 — RESOLVED 2026-08-31 — six sections, written under two rules

`/privacy` now renders six sections: what this build actually does with the
data, who will control it once eBPCO is live, what will be collected, why, the
citizen's RA 10173 rights and the route to the NPC — and, last, what is **not
yet determined**.

Two rules governed the writing, and both are recorded in `legal-copy.ts` so the
next editor inherits them.

**1. Describe what the system actually does, not what it will do.** The old text
asserted the data "is handled in accordance with the Philippine Data Privacy
Act" — an assurance, not a disclosure, and one an in-memory build cannot
evidence. The notice now leads with the truth, which is also more reassuring
than the assurance was: everything stays in the browser's memory, is transmitted
nowhere, and is erased on close or refresh. It says plainly not to file a real
application through this build.

**2. Never invent an LGU fact to fill a gap.** Retention period, the Data
Protection Officer's identity and the list of recipient offices are the
Municipality's to state. Rather than write a plausible "we keep your data for
five years" — a fabrication with legal weight — the notice has a *Not yet
determined* section that names all three as outstanding and says they will be
replaced with the Municipality's own answers before any real application is
handled.

The controller and the quoted confidentiality undertaking are sourced: the
Municipality's own Data Privacy Notice, printed at the foot of
`assets/LGU Castilla BPCO Forms/Zoning Checklist.pdf`, names the **Local
Government Unit of Castilla**.

The Profile page's Legal tab still shows the headline plus "Read full Privacy
Policy", so the two cannot drift.

### F-8 — MEDIUM — Every visitor's IP is disclosed to Google before the page renders

`src/index.html` preconnects to `fonts.googleapis.com` / `fonts.gstatic.com` and
loads Gothic A1 at runtime. On a government portal that collects personal data,
every visit hands a third party the visitor's IP address and user-agent, which
the one-sentence privacy policy does not disclose. It is also a hard external
dependency for the site's typography.

The mobile app had exactly this defect and closed it by bundling the typeface
(commit `1026ae6`). Same fix applies here: vendor the woff2 files into
`public/` and serve them first-party.

### F-8 — RESOLVED 2026-08-31 — self-hosted, Latin only

The Google links are gone from `index.html`. Gothic A1 is bundled in
`public/assets/fonts/` and declared in a new `src/fonts.scss`, registered ahead
of `styles.scss` in `angular.json`.

**Only the Latin subsets are bundled — 10 files, 152.8 kB.** Gothic A1 is a
Korean typeface and Google serves it in **495 subset slices** across these five
weights. The portal is English and Filipino, so the Korean, Cyrillic, Greek and
Vietnamese slices would have been roughly 150× the bytes for glyphs no screen
here renders. Google's own `unicode-range` values are copied verbatim, so a
browser still downloads only the slice it needs, and any Korean string would
fall through to the system stack rather than fail to render. `font-display: swap`
preserves the behaviour of the old link's `&display=swap`.

**Guarded by a build-time check, not a unit test** — `npm run check:assets`
(`scripts/check-no-third-party-assets.mjs`). This asks a question about *files*,
and the unit-test runner compiles through Angular in a browser-like context
where reading the repo is the wrong tool; the first attempt failed on
`Cannot find name 'node:fs'`. The gate inspects only tags that actually cause a
fetch, so the comment in `index.html` naming those hosts does not trip the gate
on itself — a gate that fails against its own explanation is one nobody keeps.
It also asserts every declared face file **exists**, because a missing woff2
would silently fall back to the system stack and leave the fix looking applied
while doing nothing.

## F-13 — NEW, found while resolving F-12 — 13 of 14 bundled LGU forms were unreachable

Chasing one unreferenced PDF turned up something larger:
**`core/domain/permit-form-assets.ts` had zero imports.**

Its 110 lines map every permit type to the Municipality's own blank form in
`public/assets/permit-forms/` — and nothing rendered it. Only
`unified-application-form.pdf` was reachable at all, through a hard-coded href
on the permit document page. The other 13 bundled forms could not be opened from
any screen.

**This corrects the praise in this report.** "Every path referenced in code
resolves to a file that exists — zero dead asset links" was *true* and
*misleading*: the paths resolved because `permit-form-assets.ts` named them,
while nothing imported that module. A file-existence check cannot see this.
**Trace the operation, not the file.**

**Fixed** by wiring the module into the permit catalogue: opening a permit's
requirements now offers "Download the official blank form — {label}", and says
so honestly when a type falls back to the generic Unified form.

**The guard failed its own break-check first, and that is the lesson.** The test
rendered `ALL_TYPES[0]` — a Building Permit, whose form *is* the Unified
Application Form. Collapsing every link back to the hard-coded href still passed
28/28. It now picks a type whose form is deliberately distinct, and the revert

## Screen-by-screen sweep, 2026-08-31 — F-14 to F-17

The first pass reached 7 screens. Reading the remaining 20 found three more
defects and one note. All three share a shape: **a control or a message that
is correctly wired and still tells the citizen something untrue.**

### F-14 — CRITICAL — every success message claimed the Municipality received something

The wizard's submit said **"Application submitted successfully."** Nothing was
sent. A citizen completes five steps, attaches land titles and IDs, ticks two
declarations, and is told their building permit application is filed with
Castilla. They may let construction proceed on that belief.

Four messages, same class:

| Screen | Said | Truth |
|---|---|---|
| Application wizard | "Application submitted successfully." | saved to browser memory |
| Payment flow | "Payment submitted. It is now awaiting verification." | nobody will verify it |
| Register business | "{name} has been registered." | not registered with anyone |
| My Documents | "{file} added to My Documents." | **name, type and size only — the file's contents are discarded** |

**And the existing disclosure was worse than absent — it was late.** Three
screens did carry "this demo build keeps data in memory only", and all three
carried it *only in their "we couldn't find that application" branch*. The
citizen saw it after their data was already gone, and never before investing an
hour in the wizard. **A disclosure that appears only on failure is a
consolation, not a warning.** The wizard itself had none at all.

**Fixed** by moving the disclosure to where it belongs — the app shell, above
the router outlet, on every signed-in screen, not dismissible. The build is a
demonstration, so the notice is a property of the *build*, not of a screen. It
names what is lost, that nothing reaches the Municipality, and the real MEO
number. A test asserts it renders *before* the outlet: a notice below the fold
on a long wizard is a notice nobody reads in time. All four messages now say
what actually happened.

### F-15 — HIGH — the Notification Preferences panel configured nothing

Eight checkboxes, bound with `[(ngModel)]` to `prefs = defaultNotificationPreferences()`
— a fresh local object, with **no save control and no persistence call
anywhere**. Toggling one changed a value discarded on navigation.
`AuthService.notificationPreferencesFor()` existed to serve this and returned a
new default object every call; nothing called it.

**This corrects the praise in this report.** "No dead controls — every `<select>`
is bound and every `<button>` has a handler" was true and missed this entirely.
**Bound is not persisted.** A dead-control scan looks for missing wiring; this
was wired to something discarded. Same lesson as F-13: trace the operation.

**Fixed** by storing preferences on the account like every other profile field,
with a Save control, so the panel works end to end within the demo's own world —
the standard the mocked login already met. `notificationPreferencesFor()` hands
out a copy, so an unsaved edit cannot leak into the account; a test covers that.

### F-16 — MEDIUM — a dead instruction pointing at a control that does not exist

After registering, the citizen was told: *"Please verify your email and mobile
number from your Profile before submitting a permit application."*

Three things wrong at once. **Profile has no verification action** — only two
read-only badges. **Nothing can send a verification email or an OTP**, because
nothing here sends anything. And **the verified/pending status gates nothing**
anywhere in the app, so it was not even a real precondition.

Worth noting it was not the worse failure it could have been: had the status
been *enforced*, a newly registered citizen would have been permanently locked
out — able neither to verify nor to proceed.

**Fixed:** the screen now says verification is unavailable and blocks nothing,
and the Profile badges say the same beside them. Not restorable without building
the control it names — the F-5 rule.

### F-17 — LOW, filed not fixed — self-minted business registration numbers

`business.store.ts` mints `REG-{year}-{seq}` and the business list renders it as
**"Reg. No."**. A business registration number is issued by the DTI, the SEC or
the LGU's licensing office — never by this portal. Same class as the permit
number in F-2, without the print-and-carry risk, and now covered by F-14's
shell-wide banner. Left for whoever settles what this field should hold once a
backend exists.

Stated plainly, because the finding count above is not the whole picture:

- **All 14 LGU forms are the real Castilla ones**, bundled locally, and every

- **No dead controls.** Every `<select>` is bound and every `<button>` has a

## Running it — F-18, F-19, and what only clicking found

The production bundle was served with an SPA fallback mirroring `netlify.toml`
and driven in headless Chromium. **Every finding above this point came from
reading. These two did not, and could not have.**

**A method note first.** Driving by `page.goto('/applications/...')` bounced
straight to the login screen every time. That is correct behaviour, not a bug —
the session is in-memory, so any page load logs out, exactly as `auth.service.ts`
documents. Everything after sign-in must be driven by in-app clicks. It is also
worth stating plainly as a citizen-facing property: **a refresh or a shared deep
link loses the session.**

### F-18 — HIGH — "Print / Download" produced a permit with its right half missing

The permit document lives inside the app shell, and the shell printed with it.
The rendered PDF carried the navigation sidebar down the left, and the entire
right half of the permit fell off the sheet: the municipality name, the permit
title, the owner's business and address, the whole **AMOUNT** column.

`@media print` did exactly two things — remove the page border and hide
`.no-print`. It had never accounted for the shell. "Print / Download" is the
primary action on that screen, and it is the artifact that leaves the building.

**A second defect in the same block, and the more dangerous one.** The watermark
is `rgba(150, 20, 20, 0.14)` with `print-color-adjust: economy`, the default —
under which a browser is free to drop a light decorative tint to save ink. That
would hand back precisely the clean, letterheaded, unwatermarked document F-2
exists to prevent. The screen was never the risk; the paper was.

**Fixed:** print now hides `.ds-sidenav` and `.ds-topbar`, resets `.ds-main` to
full width, and forces `print-color-adjust: exact` on both the watermark and the
demo notice. The notice is deliberately kept in the printed output — a
disclosure that lives only on the screen does not travel with the artifact, and
the artifact is what someone else is shown.

Guarded by a new gate, `npm run check:print`, because an `@media print` rule only
applies at a page boundary and no unit test can see it. Reverting either half
fails it.

### F-19 — MEDIUM — invented fees printed under a named legal authority

The document's ASSESSMENT table showed **₱5,250.00**, "Filing / Processing Fee",
AUTHORITY **"LGU Fee Schedule"** — on Republic of the Philippines letterhead.
Four amounts (₱5,250 filing, ₱850 zoning, ₱3,200 renewal, ₱1,500 amendment), all
invented, all citing that basis.

**The attribution is the defect, more than the number.** An unsourced figure
invites a phone call to the Municipality; a figure citing the LGU's fee schedule
does not. A citizen would budget on it.

Checked before filing as blocked: no bundled document carries Castilla's fee
schedule — the peso figures under `docs/` are formatting examples in a microcopy
style guide. The amounts stay, because the assessment and payment flow needs
numbers to demonstrate anything; the false attribution is now
`Illustrative amount — not a Castilla rate`, with the real ordinance title to
replace it when supplied.

### Also fixed, spotted on screen

The sidebar read **"eBPCO Portal"** while the landing page read "eBPCO Citizen
Portal". The vocabulary pass had grepped for "User Portal" and this string does
not contain it — a reminder that a rename sweep keyed on the *old* word misses
every variant that simply omits it.

## Accessibility pass — F-20 to F-22

axe-core (WCAG 2.0/2.1 A and AA) across nine screens, plus manual keyboard
checks. **Three real defects, and three false alarms that were worth not
"fixing".**

### F-20 — CRITICAL — no form control in the portal was programmatically labelled

**50 controls, 49 visible `<label>` elements, and zero `for` attributes** — not
one, anywhere in the app. Every label was a *sibling* of its control:

```html
<div class="field"><label>First Name*</label><input class="input" [(ngModel)]="firstName" /></div>
```

Sighted users saw a labelled form. A screen reader announced "edit text, blank"
for all of it — including the **entire registration form**, where a citizen
enters their name, birth date, sex, civil status and full address, and the
**entire profile form**. Two `<select>` elements (Sex, Civil Status) had no
accessible name at all.

**Fixed:** 44 controls given `for`/`id` pairs. `for`/`id` was chosen over
wrapping the input inside the label because `.field label` is `display: block`
with a bottom margin — wrapping would have shifted spacing on every form in the
app. This change has **zero visual effect**.

Guarded by `npm run check:labels`, which walks every template and fails on a
`<label>` adjacent to a control without a `for`, or a control without an `id`.
A visual check can never catch this class: the screen looks correct.

### F-21 — SERIOUS — a gold badge under the AA contrast floor

`.badge-gold` rendered `--gold-700` `#96690f` on `--gold-100` `#faefd6` =
**4.25:1**, below the 4.5:1 floor for 12px bold text. Six badges on How It Works,
one token. `--gold-700` is now `#8c6210` — **4.75:1**.

### F-22 — SERIOUS — inline links distinguishable by colour alone

WCAG 1.4.1. Fixed with underlines on inline links in prose, excluding buttons
and navigation chrome.

**Worth recording: my first selector keyed on `<p>` and missed the two
highest-traffic instances** — "Don't have an account? *Register*" and "Already
have an account? *Log In*" both sit in a plain `<div>`. Keying on the container
was the mistake; the rule now keys on the *link*, with navigation excluded.

### Three false alarms — measured, then dismissed

Naming these because acting on any of them would have damaged a design that was
already correct.

| Reported | Reality |
|---|---|
| Landing "Get Started" at **1.08:1** | axe sampled **mid-animation**. 0 failures once `.anim-fade-rise` settles. |
| 13 contrast failures on How It Works | Only **6 were real** (the gold badge). The other 7 were the same fade-in artifact — the ratios degraded monotonically down the list, which is the tell. |
| Input focus ring: transparent, zero-size, border unchanged | Measured **mid-transition**. `.input` transitions `box-shadow`; after 600ms it is a red border plus a 3px halo. Focus visibility is fine. |

**The lesson, twice in one pass: measure after animations and transitions
settle, or a CSS timing artifact reads exactly like a contrast or focus
defect.** My own check even printed `ring changes on focus: true` while the
measured values showed nothing visible — a string difference, not a visual one.

Also confirmed working, not defects: `prefers-reduced-motion` is honoured in
five stylesheets, and tab order on the auth screens is logical.

### Terminology

**Say CITIZEN** (owner ruling, 2026-08-31). Citizen, business owner, applicant
and user are four names for the same person; "citizen" is the canonical one from
now on, and this report's older sections still carry the earlier wording.

eBPCO has exactly **three** user types — **PUBLIC** (the information website),
**CITIZEN** (this portal and the mobile app, one type across two surfaces in
parity) and **ADMIN** (LGU staff). **Only ADMIN has sub-types**, driven by
accessibility built into the system. Do not model citizen sub-roles.

Worth noting where those boundaries meet in this repo: `/verify/:permitNumber`
needs no account, so it is a **PUBLIC** surface living inside the CITIZEN app —
which is exactly why F-3 mattered.

### Vocabulary pass — DONE 2026-08-31, and deliberately small

The census found 148 occurrences of applicant / user across `src/`. **Six were
changed.** A blanket replace would have been wrong, and the reason is worth
keeping:

**"Citizen" names WHO uses this portal. "Applicant" names WHICH ROLE they signed
a statutory form in.** The LGU's own Unified Application Form for Building
Permit reads "BOX 1 (TO BE ACCOMPLISHED IN PRINT BY THE APPLICANT)",
"OWNER/APPLICANT", "BOX 3 APPLICANT", and treats Applicant, Lot Owner and
Licensed Architect / Civil Engineer as three distinct signing roles across boxes
3, 4 and 5. One citizen may be the applicant without being the lot owner — hence
the catalogue's "Owner's Written Consent (if applicant is not the lot owner)".
Renaming those would misstate a legal document.

Changed — product copy naming the audience:

| Where | From | To |
|---|---|---|
| `landing.page.html` brand | eBPCO **User** Portal | eBPCO **Citizen** Portal |
| `how-it-works.page.ts` brand | eBPCO **User** Portal | eBPCO **Citizen** Portal |
| `index.html` `<title>` | eBPCO **User** Portal | eBPCO **Citizen** Portal |
| Help FAQ "Is my data secure?" | "another applicant" | "another citizen's account" |
| `status.model.ts`, `document.model.ts` comments | applicant-facing | citizen-facing |

Kept, on purpose: `<h2>Owner / Applicant</h2>` on the generated permit document,
the `Owner's Written Consent` requirement text, and every code identifier —
`ApplicantStatus`, `ApplicantType`, `applicantId`, `UserAccount`. **Renaming a
field is not renaming a key.**

The same FAQ answer also still carried the pre-F-6 assurance ("handled in
accordance with the Philippine Data Privacy Act"); it now states what the build
actually does and points at the full notice.

**The npm package and directory stay `ebpco-user-portal`.** `netlify.toml`
publishes `dist/ebpco-user-portal/browser`; renaming the project would move the
build output and break the deploy for a vocabulary change. Identifier, not copy.

The `<h2>Owner / Applicant</h2>` heading is now guarded by a test and an
explanatory comment, so a future blanket replace fails loudly rather than
quietly misstating the form.
